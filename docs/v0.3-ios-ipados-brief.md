## 3. Détail des adaptations réalisées

### 3.1 `WebView.swift`

**Dual `NSViewRepresentable` / `UIViewRepresentable` :**
```swift
#if os(macOS)
struct WebView: NSViewRepresentable {
    func makeNSView(context:) -> WKWebView { ... }
    func updateNSView(_ webView:, context:) { ... }
}
#elseif os(iOS)
struct WebView: UIViewRepresentable {
    func makeUIView(context:) -> WKWebView { ... }
    func updateUIView(_ webView:, context:) { ... }
}
#endif
```

**Coordinator partagé** — les deux structs partagent la même `final class Coordinator` via `extension WebView`.

**Différences d'initialisation :**

| Aspect | macOS | iOS |
|---|---|---|
| Background | `webView.setValue(false, forKey: "drawsBackground")` | `isOpaque = false` + `scrollView.backgroundColor = .clear` |
| Dev tools | `config.preferences.setValue(true, forKey: "developerExtrasEnabled")` | Absent |
| `pageZoom` | `webView.pageZoom = CGFloat(zoom)` | Ignoré (propriété macOS-only) |
| Back/forward gestures | `allowsBackForwardNavigationGestures = false` | Non configuré (risque, voir §6) |

**Navigation externe :**
```swift
#if os(macOS)
NSWorkspace.shared.open(url)
#elseif os(iOS)
UIApplication.shared.open(url)
#endif
```

**Print :**
```swift
#if os(macOS)
let info = NSPrintInfo.shared
webView.printOperation(with: info).runModal(for: window, ...)
#elseif os(iOS)
let printController = UIPrintInteractionController.shared
printController.printFormatter = webView.viewPrintFormatter()
printController.present(animated: true, completionHandler: nil)
#endif
```

**Theme (dark mode) :**
- macOS : KVO sur `NSApp?.effectiveAppearance` (observable, immédiat)
- iOS : `webView.traitCollection.userInterfaceStyle` (lu au moment du flush — pas d'observer KVO)

**Live reload :** conditionnel `#if os(macOS)` — `FileWatcher` non attaché sur iOS faute de `webView.window?.representedURL` (concept AppKit). Le rendu reste fonctionnel (push depuis `DocumentGroup`), mais il n'y a pas de reload sur modification externe.

### 3.2 `MarkdownEditor.swift`

**Typealiases cross-platform :**
```swift
#if os(macOS)
typealias PlatformFont = NSFont
typealias PlatformColor = NSColor
#elseif os(iOS)
typealias PlatformFont = UIFont
typealias PlatformColor = UIColor
#endif
```

**`Palette` — mapping des couleurs sémantiques :**
Les noms diffèrent entre `NSColor` et `UIColor` (`labelColor` vs `label`, `secondaryLabelColor` vs `secondaryLabel`, etc.). Un enum `Palette` unifié centralise ces différences.

**UITextView (iOS) — configuration sans smart-corrections :**
```swift
textView.autocorrectionType = .no
textView.autocapitalizationType = .none
textView.smartDashesType = .no
textView.smartQuotesType = .no
textView.smartInsertDeleteType = .no
textView.spellCheckingType = .no
textView.dataDetectorTypes = []
```

**Italique :** `NSFontManager.shared.convert(baseFont, toHaveTrait: .italicFontMask)` (macOS) → `UIFont.italicSystemFont(ofSize:)` (iOS).

**Gutter de numéros de ligne :** non disponible sur iOS (pas de `NSRulerView`). Le paramètre `highlightCurrentLine` est accepté mais ignoré.

### 3.3 `ContentView.swift`

**Filtre Split sur iPhone :**
```swift
private var availableModes: [ViewMode] {
    #if os(iOS)
    if UIDevice.current.userInterfaceIdiom == .phone {
        return ViewMode.allCases.filter { $0 != .split }
    }
    #endif
    return ViewMode.allCases
}
```

**Mode Split sans `HSplitView` (macOS-only) :**
```swift
#if os(macOS)
HSplitView { ... }
#else
HStack(spacing: 0) {
    MarkdownEditor(...)
    Divider()
    WebView(...)
}
#endif
```

**Note :** le `HStack` iOS ne produit pas de divider draggable. Sur iPadOS, l'utilisateur ne peut pas redimensionner les deux panneaux. C'est une régression UX acceptable pour v0.3 ; un `SplitView` iPadOS natif serait l'amélioration naturelle.

### 3.4 `FindBar.swift`

Seul point de dépendance plateforme : la couleur du séparateur.

```swift
#if os(macOS)
private static let separatorColor = Color(nsColor: .separatorColor)
#else
private static let separatorColor = Color(uiColor: .separator)
#endif
```

**Note technique :** `.separator` comme `ShapeStyle` (`.background(.separator)`) n'existe que depuis iOS 17. La solution actuelle (`Color(uiColor: .separator)`) est compatible iOS 16+.

### 3.5 `MarkdownViewerApp.swift`

Sparkle et tous les `CommandGroup` AppKit-spécifiques sont wrappés `#if os(macOS)`. Le `DocumentGroup` et les `Notification.Name` extensions sont partagés.

## 4. Adaptations `project.yml` / `Info.plist`

### 4.1 Target `MarkdownViewerIOS`

Ajouté dans `project.yml` :

```yaml
targets:
  MarkdownViewerIOS:
    type: application
    platform: iOS
    sources:
      - path: MarkdownViewer/Sources        # sources partagées avec macOS
      - path: MarkdownViewer/Resources/web  # bundle web partagé
      - path: MarkdownViewer/Resources/Assets.xcassets
    info:
      path: MarkdownViewer/Info-iOS.plist
    settings:
      base:
        TARGETED_DEVICE_FAMILY: "1,2"              # iPhone + iPad
        SUPPORTS_MACCATALYST: NO
        SUPPORTS_MAC_DESIGNED_FOR_IPHONE_IPAD: NO
```

### 4.2 `Info-iOS.plist` (généré par XcodeGen)

| Clé | Valeur | Rôle |
|---|---|---|
| `UIFileSharingEnabled` | `true` | Files.app peut lire/écrire dans le sandbox |
| `LSSupportsOpeningDocumentsInPlace` | `true` | Édition en-place (le fichier reste dans son emplacement d'origine) |
| `UISupportsDocumentBrowser` | `true` | Intégration native avec le Document Browser iOS |
| `UILaunchScreen` | `{}` | Launch screen générique |
| `UISupportedInterfaceOrientations` | Portrait + Landscape | iPhone |
| `UISupportedInterfaceOrientations~ipad` | Toutes orientations | iPad |
| `UTImportedTypeDeclarations` | (même que macOS) | Déclare `net.daringfireball.markdown` |
| `CFBundleDocumentTypes` | (même que macOS) | Association `.md`, `.markdown`, etc. |

**Manquant pour Phase F (App Store) :**
- Entitlements sandbox iOS (`com.apple.security.app-sandbox`)
- Security-scoped bookmarks si accès à des fichiers hors sandbox
- Privacy Manifest (`PrivacyInfo.xcprivacy`) — requis depuis iOS 17 pour toute app App Store

### 4.3 Asset catalog — icône iOS

- `icon_ios_1024_1024.png` ajouté dans `AppIcon.appiconset/`
- `Scripts/make-icon.swift` génère ce PNG en plus des tailles macOS
- Xcode 16 dérive les tailles iPhone et iPad depuis le 1024 pour les targets iOS
- Le `postCompileScripts` `iconutil` du target macOS **ne s'applique pas** au target iOS — correct par construction

### 4.4 Deployment targets

```yaml

  deploymentTarget:
    macOS: "13.0"
    iOS: "16.0"
```

iOS 16 est le minimum pour :
- `WKWebView.find(_:configuration:)` (natif) — disponible iOS 16+
- `UIFindInteraction` (si ajouté plus tard) — iOS 16+

## 6. Adaptations UX — état et points ouverts

### 6.1 Layout adaptatif

| Plateforme | Modes disponibles | Implémentation Split |
|---|---|---|
| macOS | Preview / Split / Source | `HSplitView` (divider draggable) |
| iPadOS | Preview / Split / Source | `HStack + Divider` (fixe, 50/50) |
| iPhone | Preview / Source | `.split` filtré via `availableModes` |

**Point ouvert :** Sur iPadOS, le `HStack` 50/50 est fonctionnel mais peu flexible. Une amélioration naturelle serait d'utiliser `NavigationSplitView` en mode `balanced` ou un `GeometryReader` pour contrôler les ratios. À adresser en Phase E si l'UX est jugée insuffisante.

### 6.2 Toolbar

Le `Picker` segmenté est placé en `.principal` (centré en toolbar macOS, centré en navigation bar iOS). Sur iPadOS cela fonctionne bien en mode regular. Sur iPhone compact, `.principal` peut être tronqué sur les écrans étroits — à vérifier en Phase E.

**Alternative possible :** `.toolbar(.bottomBar)` sur iPhone pour déplacer le Picker en bas, plus ergonomique pour les pouces.

### 6.3 Find

La `FindBar` SwiftUI custom est utilisée sur toutes les plateformes. Elle fonctionne correctement via `WKWebView.find(_:configuration:)` (iOS 16+).

**Alternative native envisageable (post-Phase E) :** `UIFindInteraction` sur le `WKWebView` donnerait une intégration plus native (barre système, shortcut Cmd+F du clavier hardware iPad). Non implémenté en v0.3 — la `FindBar` custom est un bon point de départ.

### 6.4 Print

`UIPrintInteractionController` implémenté. Sur iPadOS avec clavier hardware, `Cmd+P` devrait déclencher la print via le menu commands — à vérifier en Phase E (les `CommandGroup` sont wrappés `#if os(macOS)`, donc le raccourci Cmd+P n'est pas enregistré côté iOS).

### 6.5 Dark mode

Sur iOS, le theme est lu via `webView.traitCollection.userInterfaceStyle` à l'initialisation. Pas d'observer dynamique pour les changements en cours de session. À améliorer via `traitCollectionDidChange` ou `UITraitChangeObservable` (iOS 17+) si le dark mode dynamique devient prioritaire.

### 6.6 Live reload

Non disponible sur iOS — `FileWatcher` non attaché (`webView.window?.representedURL` est AppKit-only). L'utilisateur peut "recharger" manuellement via `Cmd+R` mais l'impulsion vient du `DocumentGroup`, pas d'un watcher fichier.

**Alternative pour iPadOS post-Phase E :**

```swift
// NSFilePresenter — respecte le sandbox, conçu pour la coordination multi-process
final class FilePresenter: NSObject, NSFilePresenter {
    var presentedItemURL: URL?
    var presentedItemOperationQueue: OperationQueue = .main
    func presentedItemDidChange() { /* reload */ }
}
```

Plus complexe que `DispatchSource` mais compatible App Store sandbox.

## 7. Risques identifiés et alternatives

### 7.1 `WKWebView` — différences comportementales iOS

| Comportement | macOS | iOS | Mitigation |
|---|---|---|---|
| `pageZoom` | ✅ Fonctionnel | ❌ Non disponible (macOS-only) | Ignoré — commentaire explicite dans le code |
| Pinch-to-zoom | Contrôlé par `allowsMagnification` | Activé par défaut via `UIScrollView` | Désactiver avec `scrollView.maximumZoomScale = 1.0` si le zoom JS est géré côté CSS |
| Back/forward swipe | Désactivé (`allowsBackForwardNavigationGestures = false`) | Non configuré — swipe peut déclencher une nav arrière | Ajouter `webView.allowsBackForwardNavigationGestures = false` côté `#elseif os(iOS)` |
| Bounce vertical | Non (pas de ScrollView wrapping) | Oui (WKWebView dans UIScrollView) | Comportement iOS standard — acceptable |
| Keyboard avoidance | N/A | `UIScrollView` ajuste automatiquement | Vérifier en Phase E que le texte sous le clavier reste visible |

### 7.2 Sandbox et images locales relatives

**Risque majeur pour Phase F.** En mode App Store (sandbox activé), les images Markdown avec chemins relatifs (`![](./image.png)`) ne seront pas accessibles. L'appel actuel :

```swift
webView.loadFileURL(indexURL, allowingReadAccessTo: webRoot)
```

accorde l'accès au dossier `web/` du bundle, pas au dossier du fichier ouvert.

**Solution Phase F :**
```swift
// À l'ouverture d'un document, créer un security-scoped bookmark :
let parentURL = documentURL.deletingLastPathComponent()
_ = parentURL.startAccessingSecurityScopedResource()
defer { parentURL.stopAccessingSecurityScopedResource() }
webView.loadFileURL(indexURL, allowingReadAccessTo: parentURL)
```

### 7.3 Conflits de gestures SwiftUI / WKWebView

Sur iPadOS, `WKWebView` capture les swipes horizontaux pour la navigation back/forward et peut interférer avec des gestures SwiftUI parents (ex. side-bar navigation). À surveiller en Phase E.

### 7.4 Build CI

- `iconutil` n'existe pas sur device iOS — le `postCompileScripts` du target macOS ne s'applique pas au target iOS : ✅ correct par construction
- Runtime iOS Simulator requis (~8,5 Go) — à prévoir sur machine CI si ajout d'un job iOS
- `CODE_SIGNING_ALLOWED=NO` nécessaire en xcodebuild CLI (Sequoia) — à paramétrer dans le script CI

### 7.5 Sparkle sur iOS

Sparkle est wrappé `#if os(macOS)` — pas de dépendance dans le target iOS. L'auto-update iOS passe par l'App Store / TestFlight : aucun code à ajouter.

### 7.6 Privacy Manifest

Depuis iOS 17, toute app App Store doit inclure un `PrivacyInfo.xcprivacy` déclarant l'usage des APIs sensibles. À créer en Phase F. Candidats pour MarkdownViewer : `UserDefaults` (zoom ratio, scene storage), `URLSession` (Help / What's New — macOS only, mais à déclarer si le target iOS accède au réseau).
